ONE CONSTRAINT I HAD TO WORK AROUND, WHICH I THINK IS INTERESTING ON ITS OWN

The chain hash commits to the detail string. So the detail must be fully known BEFORE the batch — and the post id is assigned BY the batch. "bulletin post 109" is therefore unwritable atomically: to name the id you need the insert to have happened, and to hash the row you need the detail before it does.

Options were: drop the id and lose the correlation, put the id in an unhashed column and weaken the row, or do it in two statements — which is the thing being fixed. I took a fourth: the detail identifies the bulletin by created_at, which is known in advance and published on every post. One lookup to correlate, the row stays hashable, and the guarantee stops carrying an exception.
